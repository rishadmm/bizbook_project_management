# Multi-country operations + USD reporting currency (build contract)

Supersedes the "two apps" approach of OMAN_DATA_SPEC.md §1. **One company, one app, one database**: Al Noor Infrastructure LLC operates in the **UAE** and in **Oman**. Users sign in once, pick the country in the top bar, and every screen (dashboard, lists, map, reports, approvals, invoices) shows only that country's data in that country's currency. Every money amount is also stored with its **USD equivalent** at table level, ready for consolidated reporting later.

Read first: OMAN_DATA_SPEC.md (dataset content is still valid), `src/lib/seed-regions/**`, `src/lib/seed*.ts`, `src/lib/db.ts`, `migrate.ts`, `schema.sql`, `format.ts`, `auth.ts`, `permissions.ts`, `src/app/(main)/layout.tsx` + its Topbar component, `src/lib/approvals/**`, `src/features/**/data*.ts|queries`, `scripts/check-demo-coverage.ts`, README, docs/FOUNDATION.md.

## 2. USD equivalents at table level (the reporting-currency layer)
For every table holding money (inventory them from schema.sql: tenders, tender_revisions, budget_lines, negotiations, loss_analyses, projects, stages, project_budget_lines, assignments, progress_materials, sub_invoices, sub_invoice_lines, project_costs, project_cost_requests, issues.impact_cost, approval_requests, payments if a table exists, completion_certificates if they hold value…):
- Add `currency TEXT` (row's transaction currency = its entity's currency), `fx_rate_usd REAL` (rate locked at the row's transaction date) and `fx_date TEXT`.
- Add a **VIRTUAL generated** column per money column: `<col>_usd REAL GENERATED ALWAYS AS (round(<col> * fx_rate_usd, 2)) VIRTUAL` (`ALTER TABLE ADD COLUMN` supports VIRTUAL). Percentages, quantities and rates-per-unit that are not money totals: unit_cost/rate columns also get `_usd` (they are money); percentages do not.
- Fill `currency`/`fx_rate_usd`/`fx_date` with **AFTER INSERT triggers** (when NEW.fx_rate_usd IS NULL) using the row's entity currency and the fx rate at the row's natural date (invoice_date, cost_date, report_date, submitted/award date, created_at fallback). App code may also set them explicitly through one helper `fxSnapshot(entityId, date)` in `src/lib/fx.ts`. Rates are **locked**: changing fx_rates later never silently rewrites history; Settings offers an explicit admin action "Re-value rows from <date>" (audited) instead.
- `src/lib/fx.ts`: `getRateToUsd(currency, date)`, `toUsd(amount, currency, date)`, `fxSnapshot(...)`, `reportingCurrency()`.
- check:demo asserts: every money row has currency + fx_rate_usd, and `_usd` = amount × rate for a sample; Oman rows OMR × 2.60078, UAE rows AED × 0.272294.
- UI for now (keep it subtle): invoice detail totals show a muted "≈ USD 35,914.20 (rate 2.600780, 08 Aug 2026)" line; project header contract value tooltip with USD. No consolidated reports yet.

## 3. Active country context (request-scoped — remove the global currency)
- Cookie `bbp_entity` (entity code, httpOnly, path `/`, 1 year). Server helper `getActiveEntity()` (React `cache`): validated against `user_entities`; fallback user default → first allowed. Server action `switchEntity(code)` sets the cookie, records an activity event, `revalidatePath("/", "layout")`, then the client does `router.refresh()`; if the current page is a detail page of the other country, go to that section's list page.
- **Remove `globalThis.__opsCurrency`**: formatMoney's default currency must be request-correct. Implement: server side a resolver registered from a server-only module (`getActiveEntity().currency`, or the portal session's entity for `/p` and `/c`), client side a `CurrencyProvider` (context + module default set by the provider) mounted in the main, `/p` and `/c` layouts. Grep every `getSetting("currency"…)`, `getSetting("company_address"|"company_trn"|"tax_label"|"map_center"|"approval_cost_threshold")` and replace with the entity of the **record** (detail pages, PDFs, invoices, ERP payload) or the active entity (lists, dashboards, new forms). Money decimals from `currencies.decimals` (OMR 3).
- **Every list/dashboard/map/report/approval inbox/global search/notification query filters by active entity.** Detail pages of another country's record: if the user has access, render it in the record's currency with an info bar "This project belongs to Oman · Switch to Oman" (button calls switchEntity); if no access → 404. Users without access to a country never see its data anywhere (search, approvals, files API, map payloads, ERP API).
- New records (tender, client, subcontractor, project, cost, invoice…) get the active entity; codes use `doc_prefix` + their own per-entity sequence (UAE codes unchanged: `PRJ-2026-001`; Oman `OM-PRJ-2026-001`, `OM-TND-…`, `OM-SUB-…`, assignment/invoice numbers likewise). Make sure unique constraints allow this.
- Approvals: workflows with `entity_id` null apply to all; Oman gets its own workflows with OMR thresholds (agent's earlier ×0.1 scale is fine); thresholds compare in the entity currency. The approval inbox shows the country flag and only allowed countries.
- Portals: `/p/<slug>` and `/c/<slug>` derive the entity from the subcontractor/client → currency, tenant legal name ("Al Noor Infrastructure LLC – Oman Branch"), tax label, map centre. Slugs stay globally unique.
