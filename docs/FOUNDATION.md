# Foundation reference (for module agents)

Run: `npm run seed` (wipes `data/ops.db` + `uploads/`, reseeds), `npm run dev` (port 3100), `npm run build`.

## Route conventions
- App shell (sidebar + topbar) lives in `src/app/(main)/layout.tsx`. **Modules go under `src/app/(main)/<route>`** (tenders, lost-analysis, projects, subcontractors, invoices, clients, settings, search; dashboard = `(main)/page.tsx`). Placeholder pages already exist for each: **overwrite** `(main)/<route>/page.tsx`.
- **Portal goes under `src/app/portal/[token]`** (outside the shell; `src/app/portal/layout.tsx` is a bare wrapper you may edit). Root layout is minimal (html/body/css only; Leaflet + geoman CSS imported globally).
- Pages are server components; `(main)` layout is `force-dynamic`. `params`/`searchParams` are Promises (Next 15): `const { id } = await params`.
- Server actions: `src/features/<module>/actions.ts` with `"use server"`, validate, transaction, `await logActivity(...)`, `revalidatePath(...)`. Queries in `src/features/<module>/queries.ts`. `src/features/settings/actions.ts` is an example.
- `formatMoney()` etc. are pure and safe in client components; the default currency is request-scoped (see Multi-country operations). In client components use `useCurrency()` or pass `{currency}`.
- `@/lib/session.ts` (getCurrentUser) imports server-only APIs - never import it from a client component; `setCurrentUser` lives in `session-actions.ts` ("use server") and is re-exported from `session.ts`.

## Multi-country operations (MULTI_COUNTRY_SPEC)
One company, one app, one database, several **country operations** (`entities`: `AE` = United Arab Emirates / AED, `OM` = Oman / OMR). Spec: `MULTI_COUNTRY_SPEC.md`.

**Data model (SCHEMA_VERSION 8, `migrateMultiCountry` in `lib/migrate.ts`, idempotent, upgrades a UAE-only DB in place).** Tables `currencies`, `entities`, `fx_rates`, `user_entities`; `users.default_entity_id`.
*Entity inheritance rule (one rule for the whole schema):* **root** tables carry `entity_id` (`clients`, `subcontractors`, `tenders`, `projects`, `approval_requests` as `INTEGER NOT NULL DEFAULT 1` - SQLite cannot add a NOT NULL column with a REFERENCES clause and a non-NULL default - and `approval_workflows.entity_id`, nullable = applies to all countries); **every child row belongs to the entity of its parent** (tender children -> tenders, project children -> projects, invoice lines -> invoice -> project, subcontractor children -> subcontractors, client users -> clients). Children never repeat `entity_id`; `lib/entities.ts` resolves it (`entityOfProject / Tender / Invoice / ...`, `entityOfAttachmentOwner(type, id)`) and `lib/fx-tables.ts` holds the same expressions as SQL. Assignments link a project and a subcontractor of the same entity (checked in `saveAssignment`).
*Country access:* `user_entities`; administrators (`super_admin`, `admin`) have every active country implicitly (`allowedEntityIds`, `userHasEntity`). The cookie `bbp_entity` (httpOnly, 1 year) only stores the active code; `getSession()` validates it against the user's countries on every request (fallback: user default, then first allowed), so a forged cookie never widens access. `getSession()` returns `{ user, entity, entities }`; helpers `getActiveEntity()`, `activeEntityId()` (`lib/auth.ts`).

**Request-scoped currency (no module-global server state).** `format.ts` has a resolver instead of the old `globalThis.__opsCurrency`: `lib/request-context.ts` keeps `{ currency }` in a React `cache()` (one object per server request) and registers the resolver; `getSession()` primes it with the active country's currency, `assertRecordAccess(entityId)` (`lib/entity-context.ts`) overrides it with the **record's** currency on a detail page (and returns `{ entity, foreign, active }` for the "This project belongs to Oman · Switch to Oman" bar, `components/shell/EntityBar.tsx`), the portal sessions (`getPortalSession`, `getClientSession`) prime it with the subcontractor's / client's country. Two users on different countries rendering at the same time therefore each format in their own currency. In the browser `<CurrencyProvider currency>` (mounted by the main, `/p` and `/c` layouts and by every detail page) provides `useCurrency()` for client components; `setBrowserCurrency` is ignored during SSR. Pass `currency` explicitly for amounts of a record whose country may differ from the viewer's. `currencyDecimals()` (3 for OMR/BHD/KWD/JOD) mirrors `currencies.decimals`.
*Server-action guards:* `assertUserEntity(user, entityId, what)` (`lib/entity-context.ts`; the user comes from `requirePermission()` and is passed to the record loaders, because React `cache()` is not request-scoped inside server actions) / `requireRecordAccess` - a record of an inaccessible country "does not exist". List queries take the active `entityId`; every other country's rows are filtered out (dashboard, lists, map payload, search, approvals inbox, files API, PDF, ERP payload, `/api/...`).

**Per-country values** moved from `settings` to `entities` (currency, company name/address/TRN, tax label, map centre, approval cost threshold, VAT, document prefix, CR no.); old settings keys are only the migration source. `settings` keeps the group name `company_name` and `reporting_currency` = `USD`. Codes: `nextCode(table, prefix, entityId)` (`features/tenders/conversion.ts`) and the subcontractor / assignment generators use `entities.doc_prefix` with a sequence per country (`PRJ-2026-001`, `OM-PRJ-2026-001`, `OM-TND-…`, `OM-SUB-…`, `OM-SC-…`, `OM-CC-…`).

**Approvals.** `approval_requests.entity_id` is the document's country; `selectWorkflow` filters `entity_id IS NULL OR = country` and prefers the country's own workflow; `resolveApprovers` only returns users who may work in that country (a department head without access is replaced by the department's accessible users); thresholds compare in the country's currency (Oman workflows are the AED ones x 0.1, in OMR); the inbox shows the flag and only the active country. Settings > Approvals edits the active country's cost threshold, Settings > Countries every country's.

**USD equivalents (reporting currency layer).** `lib/fx-tables.ts` lists the 16 money tables (tenders, tender_revisions, budget_lines, negotiations, loss_analyses, projects, stages, project_budget_lines, assignments, progress_materials, sub_invoices, sub_invoice_lines, project_costs, project_cost_requests, issues, approval_requests; completion certificates hold no money). Each gets `currency`, `fx_rate_usd`, `fx_date`, a **VIRTUAL generated** `<col>_usd = round(col * fx_rate_usd, 2)` per money column (4 decimals for per-unit rates: `unit_cost`, `unit_rate`, `rate`) and an **AFTER INSERT trigger** `trg_fx_<table>` that fills the three columns when the application did not (currency = the row's entity currency through its parent, date = the row's natural date, rate = the latest `fx_rates` row effective on or before it). Rates are **locked**; `revalueFrom(date)` (`lib/fx.ts`, Settings > Currencies & FX rates, audited as `fx_updated`) is the only way to re-value history. `getRateToUsd`, `toUsd`, `fxSnapshot(entity, date)`, `reportingCurrency()` in `lib/fx.ts`. UI: invoice detail shows "≈ USD … (rate …, date)", project contract value has a USD tooltip, the ERP payload carries `reporting` (USD, rate, date). Generated columns are returned by `SELECT *`; never `INSERT` without a column list.

**Seed.** `npm run seed` (`src/lib/seed.ts`) wipes in place, re-creates the reference data (`ensureEntities`), then runs `seedRegion(profile)` (`src/lib/seed-engine.ts`) for the UAE profile first (ids identical to the single-country dataset) and the Oman profile second, both into the same database, each into its entity. Profiles live in `src/lib/seed-regions/{types,uae,oman,index}.ts` (`entity`, `sharedUserSlots`, tenant values, users, clients, subcontractors, tenders, projects, geometry, templates, assignments, issues, portal teams, invoice catalog, approval texts). Shared staff (GM, estimator, finance, engineer, HSE) are created once by the UAE run and reused by Oman; the Oman-only staff have `@alnoor.demo` emails and OM access only. The post-passes (`seedPortal`, `seedClientPortal`, `seedInvoiceDetails/Documents`, `seedApprovalDemo`) take the entity id and only touch that country's rows. **The UAE rows must stay identical when the engine changes**: seed a scratch DB before/after and diff a dump of the business tables (ignoring password hashes, tokens, timestamps and the new entity/fx columns). `npm run check:demo` covers both countries (see README).

## Deviations from SPEC
- 15 tenders (not 12) so every status appears; no_bid/cancelled included.
- `format.ts` is pure (no DB import) and gets its default currency from a request-scoped resolver (`lib/request-context.ts`) on the server and from `<CurrencyProvider>` in the browser; there is no process-global currency.
- `setCurrentUser` is defined in `lib/session-actions.ts` and re-exported from `lib/session.ts` (a client component cannot import session.ts).
- `ProjectMapLazy` wraps `ProjectMapInner.tsx` (cannot self-import).
- System font stack instead of next/font (offline-safe). Clients page is a placeholder (not in module list).

## Subcontractor invoices (INVOICE_SPEC)
- Convention: **claimed (gross incl. VAT) -> certified (gross) -> less retention -> less advance recovery -> net payable**. `claimed_amount = gross_amount = subtotal + vat_amount`; `sub_invoice_lines.amount` is ex-VAT (`this_qty x rate`). Certifying spreads the certified subtotal over the lines pro rata.
- Code: `src/features/invoices/` (`calc.ts` pure maths, `lines.ts` BOQ/line parsing, `queries.ts` `getInvoiceDetail`, `erp.ts`, `pdf/`, `components/`). Page `/invoices/[id]`, PDF `/invoices/[id]/pdf`, ERP `/api/erp/invoices/[id]` (see `docs/ERP_INTEGRATION.md`).
- Attachments use `entity_type = 'sub_invoice'` (legacy `invoice` rows are renamed by the migration); activity stays under `invoice`. Upload permission = `invoices/certify` (the module has no `edit` action).
- BOQ of a subcontract = distinct items of its earlier invoice lines (or one item from the assignment); used to prefill the Record-invoice and portal forms. Portal submissions only accept BOQ items and require a `tax_invoice` file.
- PDF fonts: Manrope TTFs in `src/assets/fonts` (OFL). Seed files are written by `src/lib/seed-invoices.ts` (react-pdf is loaded with dynamic import because tsx runs the seed as CJS).

## Supplier registration + procurement foundation (SUPPLIER_TENDERING_SPEC Part A, SCHEMA_VERSION 9)
Part B (supplier tendering) builds on everything below. Migration: `migrateProcurement` in `lib/migrate.ts` (idempotent, in place; existing suppliers become `approved`, `prospect` / `onboarding` become `under_review`; trade list + document types inserted once, guarded by the setting `migr_procurement_ref`; permissions backfilled once, `migr_procurement_perm`).

**Entity rule for the new tables (same rule as before).** `subcontractors` is the root (already carries `entity_id`); `subcontractor_categories / _experience / _contacts / _documents`, `registration_reviews`, `registration_items`, `portal_notifications`, `portal_password_resets` are children of a supplier and never repeat `entity_id`. Own `entity_id` (reference data): `registration_doc_types` (NOT NULL, per country), `supplier_categories` (NULL = every country), `email_outbox` (nullable: the country of the mail). Part B roots (`rfx_tenders`, templates with nullable entity) follow the same pattern. The registration tables hold no money, so there are no FX columns in Part A.

**Subcontractor columns (new).** `registration_status` (`draft | submitted | under_review | referred_back | approved | rejected`), `registration_no` (`<prefix>REG-<year>-0001`, sequence per country and year, assigned on first submit), `registered_at, submitted_at, reviewed_by (the assigned reviewer), reviewed_at, review_note, reject_reason, resubmit_count`, company details (`legal_form, year_established, employees, turnover_band, website, cr_no, cr_expiry, vat_no, country_of_registration, regions_served (JSON), capacity_note`; `trade_license_no/expiry` and `tax_no` are kept in sync with cr / vat), `prequal_grade, prequal_valid_until, account_name, swift`, HSE (`hse_has_policy, hse_lti_rate, iso_9001/14001/45001, icv_score`), `declaration_accepted_at`. `subcontractor_documents` gained `doc_type_code` (registration doc type), `review_status, review_comment, reviewed_by, reviewed_at, version, is_current`: **a re-upload creates a new row (version+1) and sets the older ones to `is_current = 0`**; always filter `is_current = 1` for "what is on file" (expiry lists, portal list, dashboard do).

**Code map.** Pure rules: `lib/registration.ts` (statuses, wizard steps, review sections, IBAN/SWIFT validation, default categories + document types per country, regions). **Approval workflow reuse.** `subcontractor_onboarding` now accepts a checklist-complete supplier (legacy) or a registration under review without open queries. ## Supplier tendering / RFx (SUPPLIER_TENDERING_SPEC Part B, SCHEMA_VERSION 10)
**Entity rule for the new tables.** `rfx_tenders` is the root (`entity_id` NOT NULL); `rfx_templates` carry a nullable `entity_id` (NULL = every country); everything else (`rfx_scope, rfx_steps, rfx_criteria, rfx_requirements, rfx_boq_lines, rfx_committee, rfx_invitations, rfx_clarifications, rfx_addenda(+acks), rfx_events, rfx_bids, rfx_bid_responses, rfx_bid_prices, rfx_bid_history, rfx_scores, rfx_signoffs, rfx_bid_requests`) is a child of its tender / bid and never repeats `entity_id`. `entityOfAttachmentOwner` knows the attachment owners `rfx` (tender documents, addenda) and `rfx_bid` (bid files). **USD layer:** `fx-tables.ts` lists `rfx_tenders (estimate, award_value)`, `rfx_boq_lines (estimate_rate)`, `rfx_bids (total_amount, discount_amount, vat_amount)`, `rfx_bid_prices (unit_rate, amount)`. `assignments` gains `source` (`direct | tender`), `rfx_id`, `rfx_bid_id` (migrateTendering).

**Code map** (all DB code is synchronous, without next imports and with relative imports only because the approvals registry reaches it and Playwright loads the registry directly): `lib/rfx.ts` (pure: statuses, date helpers in GST, totals / arithmetic check / scoring / ranking maths), `features/procurement/rfx-core.ts` (create draft from a template, scope + stage availability, BOQ prefill, eligibility, invitations, publish, lazy `refreshRfxStatuses`, clarifications, addenda, cancel, committee), `bid-core.ts` (bids, receipts, the **sealed-bid query layer**, openings, requests / BAFO), `eval-core.ts` (evaluation matrix `evaluate()`, scores, compliance marks, COI, recommendation, sign-off, `applyAward`, `sendAwardLetters`), `queries.ts` / `portal-queries.ts` (read models), `actions.ts` / `portal-actions.ts` (server actions), `pdf/` (react-pdf: opening register, recommendation report, Letter of Award), `features/projects/assignment-core.ts` (the shared synchronous assignment insert used by `saveAssignment` and the `rfx_award` handler: identical codes, portal token, FX trigger, activity log).

**Sealed-bid rule.** Bid content and bid money are only read through `internalBids / internalResponses / internalPrices` (internal) and the portal queries (own bid only). Before the first opening: number, submitted-at, receipt hash only (no bidder, no content, no prices). Two-envelope: technical content after `tech_opening`, prices after `commercial_opening` and only for technically qualified bids. `/api/files/:id` applies the same rule to `rfx_bid` attachments (`internalMayReadBidFile`, `portalOwnsAttachment`). The tender activity log records THAT a bid arrived, never who sent it.

**Approvals.** Doc types `rfx_publish` (amount = estimate) and `rfx_award` (amount = award value) in the registry; default workflows (publication: procurement manager, + management from 250k AED / 25k OMR; award: procurement manager, project manager, + finance and country / general manager above the threshold) installed by `buildWorkflows` (and by `installRfxWorkflows` when an existing database is migrated). Registry options `excludedApprovers` (the recommender never decides the award) and `escalateFirstLevel` (no other procurement approver, e.g. Oman: the level goes to the super administrators).

**Mail outbox.** Invitation, addendum, clarification answer, bid receipt, Letter of Award and regret mails use the Part A templates through `mailSupplier` (outbox + portal notification); evaluation clarification / BAFO requests are portal notifications only. **Seed:** `lib/seed-tendering.ts` (called by `seedProcurement`): 4 templates, 32 of 40 assignments per country with an awarded historic tender (the assignment rows only get `source / rfx_id / rfx_bid_id`), 12 live tenders per country; statuses, scores and ranks come from the same `evaluate()` as the app.
